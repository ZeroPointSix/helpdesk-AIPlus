### 各节内容要点

#### 1. 是什么 / 不是什么

- **是**：坐席侧对工单做结构化 AI 分析 → 展示证据 → 人工改 → 确认写回 → 看自动处理/转人工建议  
- **不是**：完整 Captain Bot 对外自动回复、向量知识库、真实自动修、复杂权限改造  

#### 2. 快速启动

按本仓库实际环境写（Frappe bench + helpdesk app）：

- 依赖与 `bench get-app` / 已有站点启用 helpdesk  
- `bench migrate`（新 DocType）  
- `bench build` / desk 前端（若有）  
- 登录坐席账号打开工单详情  

若演示环境有固定 docker/脚本，写实；没有则写标准 bench 路径并标注「以本地 bench 为准」。

#### 3. 演示数据

- 链到 #9：`bench execute` / console 脚本用法  
- 无脚本时的手工建单：贴 2 条 subject+description（登录 A / 退款 B）  

#### 4. 主流程演示（验收核心）

编号步骤，每步**期望 UI/数据**：

1. 创建或打开样例工单  
2. 侧栏 AI 工作台 → AI 分析  
3. 查看 7 字段 + 证据 + 分支卡片  
4. 修改优先级/摘要  
5. 确认采纳 → 工单字段/Activity 变化  
6. 看 A 模拟执行或 B 缺信息清单  
7. （可选）改工单状态  

#### 5–9. 设计取舍（评审向）

| 主题 | 写清 |
|------|------|
| 模型 | 独立 `HD AI Analysis`，不污染 Ticket；多版本历史 |
| 分析 | 默认规则 mock，稳定无 Key；LLM 可插拔降级 |
| 验证 | 退款缺单号、登录推技术支持等规则后处理 |
| 确认 | 白名单写回；默认不关单 |
| 自动处理 | 仅建议 + simulate；防邮件风暴/误操作 |

#### 10. API 一览

表格：`analyze_ticket` / `get_analysis` / `list_analyses` / `update` / `confirm` / `reject` /（可选）`simulate`。

#### 11. 测试

复制 #7 的 bench 命令；说明失败时看哪类断言。

#### 12. 配置（#10）

`helpdesk_ai_provider` 等；无配置 = mock。

#### 13. 限制

- mock 非真智能  
- 未做客户门户 AI  
- 未接向量检索 / 自动发信
